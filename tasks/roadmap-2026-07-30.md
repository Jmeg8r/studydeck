### D1. Does the recorder-stub technique extend to ollama? — **YES (James, 2026-07-30)**

This is the decision the whole plan hangs on, so it goes first. **Answered yes**, so §2 runs
in full and the two guardrails at the end of this section are now binding rules, not a
proposal. The reasoning is kept below because the *limit* of the ruling is the part a future

`app/test/batchegress.test.mjs` (PR #40) settled a version of this argument for Open
Notebook. The convention in `CLAUDE.md` forbids asserting **what an external service

`/api/grade` and `/api/debrief` are in exactly the same position with respect to ollama,

> NOT covered here, deliberately: `/api/on/*`, `/api/tts/*`, `/api/grade` and `/api/debrief`

> against a stub of an API this repo does not control.

The second half of that sentence is the part #40 disproved. **Recommendation: adopt the
same rule for ollama** — a recorder may serve whatever minimum gets the route to the code
under test, and every assertion must be over the request we sent or the file we wrote.

Two guardrails travel with it, both earned by #40 and both non-negotiable if D1 is yes:
- **The fixture must be the dangerous case**, not a convenient one.
- **Every "nothing was sent" assertion carries a control** running the same fixture the

### The lapse-rate gate contract (D-c)

A readout is not a gate. "If the review heuristic's ceiling is hit after ~2 weeks" has been
the stated trigger since 2026-07-16 and has never opened, because nothing said what *hit*
means — and a threshold decided after seeing the number is not a threshold. Fixing that is
most of D-c's value; the chart is the easy half.

| | |
|---|---|
| **Metric** | lapse rate = lapsed reviews ÷ mature reviews, in the window |
| **Mature review** | a review of a card whose interval before that review was **≥ 7 days** (rung 2+ of `INTERVALS`). Reviews at 1d and 3d are still *learning* the card; counting them measures the material, not the scheduler |
| **Lapse** | a `miss` on a mature card — it had survived to a long interval and was then forgotten, which is precisely the failure FSRS would fix |
| **Denominator** | reviews, not cards. A card reviewed five times contributes five |
| **Window** | rolling **14 days**, matching the spec's own "~2 weeks" |
| **Minimum sample** | **30 mature reviews** in the window. Below that the rate is not reported at all — 1 miss in 3 is 33% and means nothing, and a gate that can be tripped by three reviews is worse than none |
| **Threshold** | **> 20%** |
| **Decision rule** | above threshold, with sample met, on **two consecutive weekly readings** → build item 7. One reading is noise |
| **Authoritative source** | `cockpit/reviews.jsonl` (append-only) joined to card interval history. The Stats view renders it; the file decides it |

The threshold is the one judgment call here — 20% is a starting line, not a measurement, and
it is written down *before* the data exists precisely so it cannot be chosen to fit the
answer. Move it deliberately, in a commit that says why, or the gate stops meaning anything.
Until the sample minimum is met the honest reading is "not enough evidence yet", which is a
third outcome and must not render as a green 0%.
